Latice Jeu de société en Java/JavaFX, repris en solo

Un jeu de plateau au tour par tour développé en équipe pendant une SAE de 1ère année de BUT Informatique, que j'ai repris seul pour le pousser bien au-delà du rendu de départ : mode solo contre une IA, aide au placement, personnalisation, historique de parties, et une interface entièrement repensée.

🎯 Le projet

Latice est un jeu de tuiles au tour par tour (dans l'esprit de Qwirkle) : deux joueurs posent des tuiles couleur/symbole sur un plateau 9×9, en respectant des règles d'adjacence, pour marquer des points. Le projet de base venait d'une SAE de groupe — fonctionnel, mais sommaire : écran d'accueil minuscule, boutons mal alignés, aucune protection contre les chemins de fichiers sensibles à la casse (donc cassé sous Linux), et surtout un jeu limité à deux joueurs humains sur le même poste.

Pourquoi le reprendre ?

  • Retravailler seul un projet de groupe : reprendre en main une base de code existante plutôt que repartir de zéro
  • Aller au bout d'une idée jusqu'au bout — un jeu qui ne se joue qu'à deux devant le même écran est un jeu qu'on ne rejoue pas
  • Pratiquer JavaFX en profondeur : navigation entre écrans, animations, persistance, drag & drop

Périmètre de la reprise

Build entièrement réparé (le projet ne compilait plus), refonte visuelle complète, ajout d'un moteur d'IA, d'une aide au placement, d'un système de profils/historique, et d'une suite de tests sur toute la logique ajoutée — sans casser la logique de jeu d'origine (les 26 tests historiques passent toujours).

⚙️ Stack technique

Composant Choix Pourquoi
Langage Java 17 LTS récente, records utilisés pour les structures de données immuables (historique, coups de l'IA)
Interface JavaFX 21 + FXML Séparation vue/contrôleur native, CSS pour le thème, drag & drop intégré
Build Maven + Maven Wrapper Aucune installation requise ; les dépendances JavaFX natives se résolvent automatiquement par OS/architecture
Tests JUnit 5 35 tests : logique de jeu d'origine + IA + format de l'historique
Persistance java.util.prefs + fichier CSV local Préférences (musique, thème, couleurs) et historique de parties sans base de données, adapté à une appli desktop mono-utilisateur

🧩 Fonctionnalités

Menu principal

  • Navigation façon jeu vidéo, écrans en fondu (Jouer, Profils, Règles, Paramètres, Crédits)
  • Choix du fond d'écran (dégradés + photos), musique et effets sonores, tout persistant

Partie

  • Mode 2 joueurs ou solo contre une IA
  • Aide au placement : surbrillance des cases légales pendant le glisser-déposer
  • Personnalisation : pseudo et couleur par joueur, mémorisés d'une partie à l'autre

Intelligence artificielle

Stratégie gloutonne : à chaque tour, l'IA évalue toutes les positions légales pour chaque tuile de son rack et joue le coup qui rapporte le plus de points, selon les mêmes règles qu'un joueur humain. Aucune dépendance JavaFX dans le moteur de décision — testable unitairement, sans lancer l'interface graphique.

Fin de partie & historique

  • Scores détaillés par joueur, vainqueur mis en avant
  • Rejouer ou retourner au menu directement depuis l'écran de fin
  • Historique des parties consultable depuis le menu principal

🏗️ Architecture

latice.metier          (logique pure, sans JavaFX — testable seule)
├── Plateau, Joueur, Rack, Pioche, Tuile, Arbitre   (règles d'origine)
├── JoueurArtificiel                                 (IA : choix du meilleur coup)
└── HistoriqueParties                                (persistance des scores en CSV)

latice.controleur       (un contrôleur JavaFX par écran FXML)
├── ControleurAccueil, ControleurDeJeu, ControleurParametres, ...
├── Musique / EffetsSonores        (MediaPlayer vs AudioClip, séparés par usage)
├── ThemeVisuel                    (fond d'écran choisi, partagé en direct entre fenêtres)
└── Navigation                     (point d'entrée commun : ouvrir le menu / démarrer une partie,
                                     réutilisé par le lancement de l'appli ET par "Rejouer"/"Menu principal")

src/main/resources/ihm/*.fxml       (mise en page de chaque écran)
src/main/resources/css/theme.css    (thème visuel partagé par tous les écrans)

🔧 Défis techniques rencontrés

Le vrai cœur du projet — les problèmes concrets résolus, pas juste la liste de fonctionnalités.

01

Réutiliser la logique de placement entre joueur humain et IA

La pose d'une tuile (calcul du score, retrait du rack, repioche, mise à jour de l'UI) ne vivait qu'à l'intérieur du handler de glisser-déposer. Plutôt que dupliquer cette logique pour l'IA, extraction en une méthode unique placerTuile(...) appelée aussi bien par le drag & drop humain que par le moteur de décision de l'IA — même code, même règles, zéro divergence possible entre les deux.

02

Un assombrissement de fond qui ne s'appliquait jamais

Pour rendre le texte lisible sur les fonds d'écran, un dégradé sombre était censé se superposer à l'image via -fx-background-color: linear-gradient(...), url(...) — une syntaxe CSS invalide en JavaFX (on ne peut pas mélanger un dégradé et une image dans la même propriété), qui échouait silencieusement sans erreur visible. Diagnostic par lecture des logs de warning JavaFX, puis correction en séparant fond et voile en deux calques distincts (StackPane : image + rectangle semi-transparent + contenu).

03

Un bouton "Fermer" qui quittait toute l'application

L'écran de fin de partie fermait la fenêtre de jeu puis affichait les résultats dans une popup ; fermer cette popup fermait donc la dernière fenêtre ouverte — et JavaFX termine l'application quand la dernière fenêtre se ferme. Un piège invisible en test rapide, mais qui aurait frustré n'importe quel joueur. Remplacé par une navigation explicite (Rejouer / Menu principal), avec la logique de démarrage de partie factorisée dans une classe Navigation réutilisée à trois endroits (lancement de l'app, nouvelle partie, rejouer).

04

Portabilité Windows / Linux / macOS

Le pom.xml d'origine ne déclarait aucune dépendance JavaFX (le projet ne compilait que dans un IDE configuré manuellement) et plusieurs chemins de ressources utilisaient une casse différente du dossier réel — invisible sur macOS (insensible à la casse) mais qui aurait cassé sous Linux. Correction des chemins, et ajout des dépendances org.openjfx : leurs artefacts embarquent des profils Maven activés automatiquement selon la plateforme de build, donc le même pom.xml télécharge le bon binaire natif (Windows/Linux/macOS Intel ou Apple Silicon) sans configuration manuelle.

🗺️ Pistes d'amélioration

  • IA plus stratégique (anticiper plusieurs coups à l'avance, pas seulement le meilleur coup immédiat)
  • Support de 3-4 joueurs (le moteur de règles est actuellement câblé pour 2)
  • Sauvegarde et reprise d'une partie en cours
  • Intégration continue (GitHub Actions) pour lancer les tests à chaque commit

💡 Ce que ce projet m'a appris

  • Reprendre en main une base de code existante (écrite par d'autres) plutôt que partir d'une page blanche
  • Concevoir une logique métier totalement découplée de l'UI, pour qu'elle reste testable et réutilisable (le même code sert au joueur humain et à l'IA)
  • Diagnostiquer un bug silencieux (CSS invalide, aucune exception levée) en isolant les changements un par un
  • Penser la portabilité multiplateforme dès la configuration du build, pas comme une correction a posteriori
